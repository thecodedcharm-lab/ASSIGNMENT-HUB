# Question 1: Theory

## 1. What is the difference between a Branch and a Tag in Git?

**Branch:**

A Branch is a separate line of development in Git. Developers use branches to work on new features or bug fixes without affecting the main branch. A branch moves forward when new commits are added.

**Tag:**

A Tag is a reference to a specific commit in Git. It is used to mark important points in the project history, such as software releases or milestones. Unlike branches, tags do not move automatically.

| Branch                                   | Tag                                    |
| ---------------------------------------- | -------------------------------------- |
| Used for development.                    | Used to mark important commits.        |
| Moves when new commits are added.        | Remains attached to a specific commit. |
| Developers create branches for features. | Developers create tags for releases.   |
| Can be merged into another branch.       | Cannot be merged like a branch.        |

## 2. What is the difference between a Lightweight Tag and an Annotated Tag?

**Lightweight Tag:**

A Lightweight Tag is a simple reference to a specific commit. It does not store additional information such as the tagger's name, date or message.

Example:

```bash
git tag v1.0
```

**Annotated Tag:**

An Annotated Tag is a complete Git object that stores additional information such as the tagger's name, email, date and a message.

Example:

```bash
git tag -a v1.0.0 -m "First stable release"
```

| Lightweight Tag                    | Annotated Tag                     |
| ---------------------------------- | --------------------------------- |
| Simple reference to a commit.      | Complete Git object.              |
| Does not contain a tag message.    | Contains a tag message.           |
| Does not store tagger information. | Stores tagger information.        |
| Useful for personal bookmarks.     | Useful for professional releases. |

## 3. Why should we prefer Annotated Tags in professional/collaborative projects?

Annotated Tags are preferred in professional and collaborative projects because they provide additional information about each release.

Advantages:

1. **Release Information:** Stores details about the release.
2. **Better Tracking:** Helps developers identify important versions.
3. **Professional Standards:** Makes project management more organized.
4. **Accountability:** Stores the tagger's identity and date.
5. **Documentation:** Allows developers to understand the purpose of each release.

## 4. What is Semantic Versioning? Explain with examples.

Semantic Versioning is a version numbering system used to manage software releases.

It follows this format:

```text
MAJOR.MINOR.PATCH
```

**1. MAJOR Version (v1.0.0)**

A major version is increased when major changes or incompatible updates are introduced.

Example:

```text
v1.0.0
```

**2. MINOR Version (v1.1.0)**

A minor version is increased when new features are added without breaking existing functionality.

Example:

```text
v1.1.0
```

**3. PATCH Version (v1.1.1)**

A patch version is increased when bugs are fixed without adding major new features.

Example:

```text
v1.1.1
```

## Step 1. Create a repository and initialize Git.

```bash
mkdir tag-version-project
cd tag-version-project

git init
git branch -M main
```

Create the first file:

```bash
echo "My Versioned Project" > README.md

git add .
git commit -m "Initial commit: Create project"
```

## Step 3. Create two Lightweight Tags.

Create lightweight tags on two different commits.

```bash
git tag bookmark-v1 HEAD~2

```

## Step 4. Create three Annotated Tags.

```bash

```

## Step 5. Display all tags.

```bash
git tag
```

## Step 6. Display tag information.

```bash
git show v1.0.0
git show v1.1.0
git show v1.1.1
```

## Step 7. Push repository and tags to GitHub.

First, create an empty repository on GitHub.

Then connect it:

```bash
git remote add origin YOUR_GITHUB_REPOSITORY_LINK

git push -u origin main
git push origin --tags
```

Replace `YOUR_GITHUB_REPOSITORY_LINK` with your actual GitHub repository URL.
